Installed and verified 2026-09-06. Access re-verified 2026-09-11 at the Pi's
current address; the service and kiosk details below have not been re-tested
since 2026-09-06.

## Access

```sh
ssh pi-glo
```

A Host block in `~/.ssh/config` on Ethan's Mac maps to `glo@145.76.18.112` with
the dedicated key `~/.ssh/id_pi_glo` and `IdentitiesOnly yes` — kept separate
from the GitHub key so neither unlocks the other.

**The address is DHCP and has already moved once.** It was `192.168.3.121` with
a second address on `192.168.3.60` on 2026-09-06, and `145.76.18.112` on
2026-09-11. When `ssh pi-glo` stops working, the address is the first thing to
check, and the fix is to edit `HostName` in that block. The host keys themselves
have not changed across the move, so a changed-key warning means a *different
machine*, not a reimaged Pi. See `open-items.md` for how that was established.

Passwordless sudo already ships on this image via `/etc/sudoers.d/010_pi-nopasswd`
(`glo ALL=(ALL) NOPASSWD: ALL`), so `sudo -n` works over SSH with no setup.

## Setting up a machine from scratch

`web/bootstrap-pi.sh` takes a fresh Raspberry Pi OS install to the point where
`install-pi.sh` can run: the apt packages, the `dialout` group so the serial
glove is readable, and lightdm auto-login. It is idempotent and was verified
against the Pi 4 on 2026-09-11.

**Flash the "with desktop" image, 64-bit, not Lite.** The kiosk session borrows
`labwc`, `lightdm`, the Pi's own Chromium packaging, `/usr/bin/labwc-pi`,
`/usr/bin/setup_env` and `/etc/xdg/labwc/*`, all of which are desktop-image only.
Choosing desktop costs nothing at runtime because the kiosk runs its own session
with no panel. `bootstrap-pi.sh` says so plainly if it detects Lite.

The full migration checklist, including the Pi 5 specifics, is in
`../docs/migrate-to-pi5.md`.

## What is installed

| | |
|---|---|
| `~/pi-glo/web/` | the app, deployed by rsync from the Mac |
| `piglo-server.service` | the visualiser, port 8080 |
| `piglo-ble.service` | the BLE bridge |
| `/etc/default/piglo` | which sensor source to use |
| `python3-bleak`, `python3-dbus-fast` | **from apt, not pip** |

Both services are enabled at boot.

**Use apt, not pip.** Debian 12 marks the system Python externally-managed
(`/usr/lib/python3.11/EXTERNALLY-MANAGED`), so `pip install` refuses. `bleak` is
0.20.2 from apt, which has no `__version__` attribute — importing it and reading
that will throw. `BLEDevice.rssi` is also deprecated in this version; read RSSI
from `AdvertisementData` in the scan callback instead.

```sh
systemctl status piglo-server piglo-ble
journalctl -u piglo-ble -f          # watch the glove connect
```

## Changing the sensor source

Edit `/etc/default/piglo`:

```sh
PIGLO_SOURCE=--idle                  # no serial glove — BLE swipe only
PIGLO_SOURCE=--port /dev/ttyACM0     # the 6-IMU hand
PIGLO_SOURCE=--simulate              # synthetic everything
sudo systemctl restart piglo-server
```

As of 2026-09-06 it was set to `--idle`, because the hand is on BLE and no
serial device is attached.

## Redeploying

```sh
rsync -az --delete --exclude __pycache__ web/ pi-glo:~/pi-glo/web/
ssh pi-glo 'sudo systemctl restart piglo-server piglo-ble'
```

## Kiosk mode — Chromium, installed and on, 2026-09-11

**It is now enabled.** Power on the Pi and it logs in, waits for the visualiser
to answer, and opens Firefox full-screen on the demo. Nothing to click.

```sh
ssh pi-glo 'cd ~/pi-glo/web && sudo ./install-pi.sh --kiosk'
ssh pi-glo 'cd ~/pi-glo/web && sudo ./install-pi.sh --uninstall'
```

Three pieces make it work, and each is somewhere different:

| piece | where |
|---|---|
| Auto-login as `glo` | `autologin-user=glo` in `/etc/lightdm/lightdm.conf`, already shipped |
| The launcher | `/usr/local/bin/piglo-kiosk`, generated by the installer |
| The hook | one marked line in `~/.config/labwc/autostart` |

**The launcher lives outside `web/`.** Deploys rsync that folder with
`--delete`, so anything generated inside it disappears on the next deploy.

**It went Chromium, then Firefox, then back to Chromium.** The round trip was
worth it, because measuring the two is what found the real bottleneck. Same
page, same screen, 1920x1080, hand at full width:

| | frame time | rate | CPU |
|---|---|---|---|
| Firefox ESR 140 | 99 ms | 11 fps | ~55% of a core |
| Chromium 152 | 33 ms | 34 fps | ~10% of a core at reduced size |

**The browser was the whole problem.** Not the scene, not the resolution, not
the GPU. See *Performance* below for everything that was ruled out first.

On labwc a browser must be told to use Wayland: Chromium needs
`--ozone-platform=wayland` or it exits with `Missing X server or $DISPLAY`.

**Chromium also needs the keyring disabled.** Without
`--password-store=basic --use-mock-keychain` it asks to unlock the login keyring
on every start, and the dialog sits on top of the demo. Both flags are in the
launcher. This is the fix, not typing the password: the kiosk stores no
passwords and has no business touching the keyring.

**The launcher waits for the server, it does not sleep.** It polls the URL for
up to 90 seconds, then launches regardless. A visible error page beats a blank
desktop that explains nothing.

**A dedicated Chromium profile** sits at `~/.config/piglo-chromium`, so the demo
never inherits the desktop user's browsing state. Chromium is configured purely
by flags, so there is no profile file to maintain.

**A user `~/.config/labwc/autostart` replaces the system one entirely.** Writing
one naively kills the taskbar, desktop icons and display config. The installer
seeds it from `/etc/xdg/labwc/autostart` first, then appends the kiosk line
between markers so it can be removed cleanly.

### Turning it off for a while

The kiosk takes the screen at every login, which is disruptive while developing.
To stop it without uninstalling the services, delete the marked block from
`~/.config/labwc/autostart` and log out. `--uninstall` removes the block and the
launcher, and leaves the profile alone.

## Performance — measured 2026-09-11, read this before optimising anything

The Pi was at load average 9.5 with the demo running. It is now around 2. Four
findings, in order of how much they mattered. Every number was measured on the
Pi, and several obvious-looking fixes turned out to do nothing.

### 1. The desktop ran twice, and that was self-inflicted

`labwc-pi` launches `labwc -m`, and `-m` is `--merge-config`: labwc then runs the
autostart in **every** XDG base directory. A user autostart does not replace the
system one, it runs **alongside** it. Seeding one therefore started the panel and
the desktop a second time, and the two panels together burned about 65% of a
core fighting each other. Hence the dedicated session above.

**The old note in this file claiming a user autostart "replaces the system one
entirely" was wrong.** It is corrected in the kiosk section.

### 2. Bluetooth scanning never stopped

`glove_ble.py` scanned for 8 seconds, waited 2, forever. With no glove in the
room that drove `bluetoothd` and `dbus-daemon` continuously, about 42% of a core
across the three processes. It now backs off to a 10 second cap and resets on
connect. The cap is short on purpose: nobody should wait for the glove.

### 3. `requestAnimationFrame` was costing 62% of a core to draw nothing

The big one, and deeply counter-intuitive. Identical page, identical work,
changing only the scheduling call:

| | idle mode |
|---|---|
| `requestAnimationFrame(tick)` | 66.6% of a core |
| `setTimeout(tick, 0)` | 4.4% of a core |

The script itself used **2ms of JavaScript per second** either way, and rendered
zero frames. Touching rAF at all appears to hold the compositor in a
continuously-animating state on this Firefox and labwc stack. So the page now
schedules ordinary work with `setTimeout`, and uses rAF **only while the hand is
actually moving**, where it is worth it for smoothness and costs nothing extra.

Things that were measured and made **no** difference, so do not bother:
antialiasing, the drawing-buffer width, the unused second WebGL context,
`gfx.webrender.all` and `widget.dmabuf.force-enabled`, and the custom session
versus the stock one.

### 4. The browser was the bottleneck, and geometry never was

Everything below in this section was measured under Firefox, and the ceiling it
describes turned out to be a Firefox ceiling. Switching to Chromium tripled the
frame rate at the same resolution and viewport size. Keep the rest of this
section anyway: it is the record of what was ruled out, and it is all still true
of the hardware.

Things measured and found **not** to be the cause, so nobody repeats them:

| change | result |
|---|---|
| Wireframe, edges only, no fill or shading | 11 fps vs 12. No better. |
| 5588 triangles down to **72** (one box per finger, one per palm) | 13 fps vs 11. 16% for 78x less geometry. |
| 5588 down to 2332 triangles, compare mode | 16 fps vs 15. Nothing. |
| Antialiasing off | no change |
| Drawing buffer 1400 to 900 | no change |
| Removing the unused second WebGL context | no change |
| `gfx.webrender.all`, `widget.dmabuf.force-enabled` | slightly worse |

So do not spend effort on the model. The hand is 5588 triangles and 8459
vertices, which sounds like a lot and is irrelevant at this scale. The only
geometry change kept was making the finger cylinders open-ended, because their
caps sit inside the joint spheres and are never visible.

**Compare with raw roughly halves the frame rate**, 34 fps down to 15. Two
viewports mean two WebGL contexts rendering and two canvases composited. If that
ever needs fixing, the route is one context with two scissored viewports rather
than two canvases.

### 5. Frame cost scales with the on-screen size of the 3D view

This is the ceiling, and it is hardware. WebGL genuinely runs on the Broadcom
GPU, not in software (checked via the unmasked renderer string).

| condition | frame time | rate |
|---|---|---|
| 2560x1440, full-width viewport | 134 ms | 7 fps |
| 1920x1080, full-width viewport | 83 ms | 12 fps |
| 1920x1080, viewport capped to 1000x500 | 50 ms | 18 fps |

So the demo now runs the screen at 1920x1080 via `PIGLO_MODE` in
`/etc/default/piglo`, and `.screen` is capped and centred in the CSS. Both are
commented where they are set. Raising either slows the hand down again.

**Smoothing must be slower than the frame time.** The easing was tuned to close
the gap in 55ms, which is shorter than a frame, so every frame snapped to the
newest pose and the motion looked stepped. `EASE_TAU` is now 0.18.

### How to measure this yourself

Instantaneous `top` samples are far too noisy for this. Accumulate CPU time over
a fixed window instead, and for frame rate put a counter on screen and read it
with `grim`, since there is no devtools on the kiosk.

**Serve with `Cache-Control: no-store`.** `server.py` now does. Without it
Firefox served a stale `index.html` after a redeploy and silently invalidated a
whole round of measurements: the page under test was not the page deployed.

## The Pi 5, and the display rules it imposes — 2026-09-11

The demo moved to a Raspberry Pi 5 (8GB, bookworm, same userland as the Pi 4).
`web/bootstrap-pi.sh` then `install-pi.sh --kiosk` took a fresh image to a
working kiosk on the first attempt, and it survives a cold boot.

Two screens: a 720x1280 DSI touch panel for whoever is presenting, and a
1920x1080 monitor or projector for the audience. They are **mirrored**, which in
wlroots means putting both outputs on the same logical area, not any browser
trick. `/usr/local/bin/piglo-displays` does this at session start from settings
in `/etc/default/piglo`.

### The rules, all of them learned by measuring

**Every display runs at its own native mode and is scaled to the shared logical
size.** Forcing both to a common low mode is what made the projector blurry: it
then receives an upscaled 720p signal rather than a real 1080p one.

**The logical size must not exceed the smallest display's native size.** Going
above it gives that display a scale below 1, and Chromium then sizes its window
wrongly and fills only part of the screen. Confirmed with a cleared browser
profile: a 1278x718 window on a 1916x1077 output.

**Prefer a logical size that makes the big screen an integer scale.** 960x540
puts a 1920x1080 monitor on exactly 2x, which is both the sharpest and the
cheapest case.

| logical | projector | frame rate | CPU |
|---|---|---|---|
| 1280x720 on both, forced | upscaled 720p, blurry | 60 fps | 55% of a core |
| 1280x720, projector native 1080p at 1.5 | sharp | 38 fps | 55% |
| **960x540, projector native 1080p at 2.0** | **sharp and twice the size** | good | **13%** |

**Pick the refresh rate explicitly.** Left alone, wlr-randr takes the first mode
listed, and monitors commonly offer 1280x720 at 23.976Hz first, which looks like
a slideshow. The fastest is wrong too: this monitor offers 144Hz against a 60Hz
panel. `PIGLO_REFRESH_MAX` caps it, default 60.

### Rotating an output does not rotate its touchscreen

This cost an afternoon. The panel is portrait and gets `--transform 90` to sit
landscape. Touch coordinates do **not** follow, so every press landed rotated:
pressing the top left registered at the bottom left.

Two things were needed, and only the second one worked:

- The stock `rc.xml` maps touch devices by names like `11-005d Goodix Capacitive
  TouchScreen`, but the kernel here reports plain `Goodix Capacitive
  TouchScreen`. No rule matched, so the device was mapped to no output at all.
  The installer now detects the real name. **Necessary but not sufficient.**
- labwc's own `<calibrationMatrix>` had no effect. What works is a udev rule
  setting `LIBINPUT_CALIBRATION_MATRIX`, which libinput reads when it opens the
  device. The installer writes `/etc/udev/rules.d/99-piglo-touch.rules`.

The matrix is derived from `PIGLO_PANEL_TRANSFORM`, and `PIGLO_TOUCH_MATRIX`
overrides it. For a 90 degree panel it is `0 -1 1 1 0 0`. **Diagnosing this is
much easier with `static/touchtest.html`**, which labels the four corners and
draws a ring where you actually pressed.

### Chromium settings that matter

`--password-store=basic --use-mock-keychain` stop it asking to unlock the login
keyring on every start, which otherwise puts a dialog over the demo. The kiosk
stores no passwords. `--autoplay-policy=no-user-gesture-required` lets the media
player start without a click, since nobody clicks a kiosk.

## Taking a screenshot on the Pi

`grim` and `scrot` are both installed. Under Wayland:

```sh
ssh pi-glo 'export WAYLAND_DISPLAY=wayland-0 XDG_RUNTIME_DIR=/run/user/1000
            grim /tmp/shot.png'
scp pi-glo:/tmp/shot.png .
```

This is the only way to verify what the Pi actually renders. Viewing the UI from
a laptop browser tests the laptop's GPU, not the Pi's.

## Flashing the Nano

PlatformIO, from the repo root:

```sh
cd ~/pi-glo/Saxion-SSP
pio run --project-dir examples/ble-tinyml-enum              # build
pio run -t upload --project-dir examples/ble-tinyml-enum    # flash
```

`-t upload` builds too; splitting them just avoids leaving the bootloader
waiting through a slow first compile (TFLite Micro takes ~4 minutes cold, ~13 s
warm).

PlatformIO triggers the 1200-baud reset itself when a sketch is running. If it
cannot find the port, **double-tap the reset button** — the orange LED breathes
slowly — and re-run immediately. Check mode via USB product id: `0x005A` is
bootloader, `0x805A` is a running sketch.

Only `external/eigen` and the `-pid` driver submodules are uninitialised, and
`ble-tinyml-enum` needs neither (eigen is in `lib_ignore`, BMI270 comes from
`lib_deps`). `fusion`, `tl` and `fmt` are vendored directly, not submodules.
